# ResearchMonitor v0.2 软件设计：零配置自动识别与单封报告

日期：2026-10-16　·　取代 v0.1 的「必须用 `rmon run` 启动」模式（`rmon run` 仍保留，作为精确模式）

## 1. 需求与对应设计

| # | 你的要求 | 设计 | 代码 |
|---|---|---|---|
| 1 | 不想装进同一个 Python 环境；软件自己看 CPU/GPU，按特征区分「我们的程序」和浏览器、系统程序 | 便携版自带 Python，双击启动；后台 agent 扫描全部进程并对每个进程打分（§3） | `discovery.py`、`tools/build_windows_bundle.py` |
| 2 | 根据 CPU、GPU 占用判断代码运行情况 | 每 15 s 把任务归入一种运行状态，连成时间线；判定疑似卡死（§4） | `tracker.py` |
| 3 | 决定何时发邮件；能识别中间结果日志就发中间结果 | 自动找日志文件和终端文字，解析 epoch / 指标 / checkpoint；中间结果按间隔发（§5、§7） | `logscan.py`、`winconsole.py` |
| 4 | 结束时根据 CPU、GPU 状态判断结束原因并说明 | 退出码 + 最后报错 + 结束前资源曲线 + 写出的文件 + 是否重启 → 结论和置信度（§6） | `infer.py` |
| 5 | 以上在一封邮件里完成（中间结果除外） | 每个任务结束时只发一封完整报告；中间结果、卡死、NaN 提醒单独发且各有上限（§7） | `engine.finalize_auto`、`render.job_report` |
| 6 | 尽可能轻量 | 单进程、低优先级、分层采样、昂贵操作只做一次；实测空闲 0.13 %、跟踪中 0.20 % 单核，内存 29 MB（§8） | `agent.py` |

## 2. 总体结构

```text
                       ┌──────────────────── 后台 agent（唯一常驻进程，低优先级）────────────────────┐
双击 Start.vbs ──────▶ │                                                                               │
                       │  每 20 s  进程扫描 ──▶ 候选打分 ──▶ 达到条件 ──▶ JobTracker（每个任务一个）   │
                       │            (discovery)                              │                         │
                       │  每 3 s   存活检查（Windows：持有进程句柄，可读真实退出码）                  │
                       │  每 15 s  CPU / 内存 / GPU / 磁盘 IO 采样 → 运行状态 → 时间线 → 卡死判定      │
                       │  每 30 s  读日志文件新增内容；每 60 s 读终端窗口文字 → 进度、指标、报错       │
                       │  结束时   infer_end() → 一封完整报告（SQLite 发件箱，失败自动重试）           │
                       │  每 10 s  发件箱 / 远程心跳；本地面板（设置页、任务、候选程序）               │
                       └───────────────────────────────────────────────────────────────────────────────┘
你的程序：照常 python train.py（终端、VS Code、PyCharm、Jupyter 均可），不需要任何改动
```

## 3. 识别「我们的程序」

### 3.1 低成本扫描
- 每 20 s 一次 `process_iter`，只读便宜字段：名字、父进程、启动时间、CPU 时间。两次扫描的 CPU 时间差就是每个进程的 CPU 占用。
- 只对「看起来相关」的新进程读昂贵字段（命令行、工作目录、可执行文件、用户、父进程链），而且每个进程只读一次。相关的定义：名字是解释器（python、pythonw、R、Rscript、julia、matlab、octave…），或者正在用 CUDA 计算，或者持续高 CPU。
- 名字在排除表里的直接跳过：系统进程、浏览器、微信 / QQ / 钉钉 / 飞书、Office、IDE 本体、网盘、播放器、NVIDIA 服务、shell 本身等。

### 3.2 打分

| 特征 | 分 |
|---|---|
| 解释器（python / R / julia / matlab …） | +2 |
| 命令里有脚本（.py/.R/.jl/.m/.ipynb/.sh）或 `-m 模块` | +1 |
| 命令里有实验词（train、eval、infer、finetune、epoch、--lr、batch、model、dataset、torchrun、accelerate、deepspeed、训练、推理 …） | +1～+2 |
| 由终端 / IDE / tmux / ssh / Slurm 启动 | +1 |
| 解释器在 conda / venv 环境里 | +1 |
| 正在用 GPU 做 CUDA 计算（解释器，或只做计算不做图形的原生程序） | +3 |
| 持续 CPU ≥ 50 %（≥ 150 % 加 2） | +1～+2 |
| 内存 ≥ 1 GB | +1 |
| 命中你的「监控」规则（脚本名、项目文件夹、关键词） | +10 |

开始跟踪需要同时满足三条：
- 得分 ≥ 5，原生程序需要 ≥ 6；
- 有活动：CPU 或 GPU 在忙；或者已运行 10 分钟以上且静态得分足够，用来覆盖只等网络的 LLM API 评测脚本；
- 已运行 ≥ 2 分钟，可在设置页修改。

### 3.3 排除与归组
- **工具和服务**：pip / conda、jupyter lab / notebook 服务端、tensorboard、语言服务器（pylance、pyright、jedi）、调试适配器、格式化和检查工具、pytest、streamlit / gradio / uvicorn 等服务器、本软件自身。这些名字必须作为命令的一部分出现才会被排除，所以名为 `black/` 或 `tensorboard_logs/` 的文件夹不会误伤训练脚本。
- **其他用户的进程**：不监控。
- **你的「忽略」规则**：不监控。
- **交互式会话**（Jupyter kernel、IPython、不带脚本的 python）：不按「进程退出」处理，而是按「计算段」处理。连续计算 ≥ 10 分钟后空闲 2 分钟，算一段结束，发一封报告。
- **一个任务的多个进程只算一个任务**：venv 启动器和真实解释器、torchrun 和各 worker、DataLoader 子进程，都向上找到最上层的同类进程作为任务的根，资源按整棵进程树汇总。
- **识别依据会被记录**：每个被识别的任务都记录得分和理由，邮件和面板里都能看到，例如「得分 9：python；train.py；keywords train,epoch；从 cmd 启动；conda 环境；使用 GPU」。
- **识别不准时**：面板首页列出「识别到但未监控」的候选程序，每个都有「监控它 / 忽略」按钮。按钮会生成一条按脚本名匹配的规则，以后同名脚本自动生效。

## 4. 判断运行情况

每次采样（15 s），按下面的顺序把任务归入一种状态，命中第一条即停：

| 状态 | 条件 |
|---|---|
| 暂停 | 进程被挂起 |
| GPU 计算 | 任务在 GPU 上，且利用率 ≥ 10 %（单进程数据）或 ≥ 20 %（整卡数据） |
| CPU 计算 | 进程树 CPU ≥ 50 % 单核 |
| 数据读写 | 磁盘 IO ≥ 5 MB/s |
| 轻负载 | CPU ≥ 5 % 或最近 1 分钟有新输出 |
| 空闲 | 以上都不满足 |

- 相邻的同一状态合并成一段时间线，报告里用彩色条和分段列表展示，例如「GPU 计算 82 % · 数据读写 9 % · 空闲 4 %」。
- **疑似卡死**：曾经计算过，之后持续空闲超过阈值（默认 30 分钟）。只提醒一次，绝不结束程序，恢复活动后自动记录「已恢复」。
- 运行中顺带记录这些情况，写进最终报告：系统内存 ≥ 95 %、显存 ≥ 98 %、GPU 温度过高、磁盘将满、loss 出现 NaN。

## 5. 读取程序输出（不需要改代码）

| 来源 | Windows | Linux |
|---|---|---|
| 重定向到文件（`> log.txt`、nohup.out） | 通过打开的文件找到 | `/proc/<pid>/fd/1,2` 直接拿到 |
| 程序自己打开写入的日志 | `open_files()`，5 分钟刷新一次 | 同左 |
| 工作目录里正在增长的日志类文件（`.log/.txt/.out/.csv/.jsonl`，含 `logs/`、`outputs/`、`lightning_logs/`、`wandb/`） | 有限深度扫描 | 同左 |
| **终端窗口里的文字**（直接 `python train.py` 时的 traceback） | 短命辅助进程 AttachConsole 后读取屏幕缓冲区；任务结束后通过父 shell 的控制台读最后一屏 | tmux 中运行时 `tmux capture-pane`；普通终端无法从外部读取 |

解析内容：
- **进度**：`Epoch k/N`、HF Trainer 的 `'epoch': 1.5`、tqdm 的 `450/1000 [02:13<02:43]`，并据此估算剩余时间。
- **指标**：`key=value`、`key: value`、字典打印、Keras 进度行、Lightning `metrics.csv`。含 val / eval / test / 验证 / 测试 等字样的记为评估结果，并维护每个指标的历史最好值（loss 类越小越好）。
- **checkpoint 保存**、**完成信号**（training complete、done、训练完成…）、**NaN / Inf loss**。

## 6. 判断结束原因

证据从强到弱：

1. **电脑重启 / 关机**：开机时间晚于最后一次看到任务，或 boot id 改变。含 Windows「快速启动」关机。
2. **真实退出码**：Windows 上 agent 识别任务时用 `OpenProcess` 持有句柄，进程结束后 `GetExitCodeProcess` 仍能读到；`rmon run` 模式由父进程拿到。
3. **程序最后的话**：输出末尾的 traceback（CUDA OOM、GPU 错误、MemoryError、普通异常、KeyboardInterrupt）、`Killed`、完成信号。
4. **结束前 5 分钟的机器状态**：系统内存 / 显存是否接近耗尽、是否仍在计算、内存是否在飙升。
5. **留下了什么**：最后 10 分钟写出的文件（结果、checkpoint）、进度是否到 100 %。

判定表（节选）：

| 证据 | 结论 | 置信度 |
|---|---|---|
| 退出码 0 | 正常完成 | 高 |
| 0xC000013A / KeyboardInterrupt | 被中断（Ctrl+C 或关闭了终端窗口） | 高 |
| 退出码非 0 + traceback | 异常退出：具体类型（CUDA 显存不足 / Python 异常 …） | 高 |
| 原生崩溃码（0xC0000005 等） | 程序崩溃 | 高 |
| 退出码 1 + 读不到输出 | 未捕获异常或被任务管理器结束 | 中 |
| 无退出码 + 末尾 traceback | 异常退出 | 高 |
| 无退出码 + `Killed` 或内存耗尽 | 系统内存耗尽被结束 | 中 |
| 无退出码 + 完成信号 / 写出结果 / 进度 100 % | 很可能正常完成 | 中～高 |
| 无退出码 + 显存满且计算中突然结束 | 可能显存不足 | 低 |
| 卡住一段时间后结束 | 可能卡住后被手动结束 | 低 |
| 其他 | 无法确定（并说明缺什么证据） | 低 |

每条结论都附带依据列表，原样写进邮件，不给没有依据的判断。

## 7. 邮件策略

- **每个任务恰好一封最终报告**：包括正常完成、失败、中断、电脑重启。发件箱按 `run:<id>:final:<状态>` 去重。报告内容：
  - 结论与置信度、依据；
  - 程序、目录、解释器、PID、识别得分与理由；
  - 运行时间线和各状态占比、运行中发现的情况；
  - 资源平均值和峰值；
  - 进度、最近训练指标、评估记录、最好结果；
  - 本次运行写出的文件；
  - traceback 和最后的输出（脱敏），失败时附上 `output_tail.txt`；
  - 处理建议。
- **中间结果**：识别到新的评估结果时发送。默认任务运行 15 分钟后才开始，之后最多每 2 小时一封，可在设置页改成「不发 / 每次 / 1h / 6h」。
- **运行中提醒**：疑似卡死、loss 出现 NaN，各最多一次。其余异常只写进最终报告。
- **默认不发重复提醒**（P1 升级提醒默认关闭），以符合「一封邮件」。需要时可在配置里打开。

## 8. 轻量化

| 措施 | 效果 |
|---|---|
| 唯一常驻进程；不为每个任务起监控进程 | 内存约 30 MB |
| 低 CPU 优先级 + 低 IO 优先级 | 永远让着实验 |
| 调度线程睡到下一个到期任务，不忙等 | 空闲时几乎不唤醒 |
| 全系统扫描只读便宜字段；昂贵字段每进程只读一次 | 300 个进程的扫描只需毫秒级 |
| 每个任务每 15 s 采样一次；日志只读新增字节；终端文字每 60 s 读一次 | 跟踪时开销几乎不增加 |
| SQLite WAL + `synchronous=NORMAL` | 写盘少 |

实测（Linux，系统上 313 个进程，扫描间隔 20 s）：

| 场景 | CPU（占单核） | 内存 |
|---|---|---|
| 空闲（没有任务被跟踪） | 0.14 % | 28.6 MB |
| 跟踪 1 个任务 | 0.20 % | 28.9 MB |

Windows 上枚举进程略慢，每分钟还会多起一次读终端文字的辅助进程，预计仍低于 1 %。面板首页会显示本软件的实时 CPU 和内存占用。

## 9. 傻瓜运行（便携版）

- 解压 `ResearchMonitor-0.2.2-windows-x64.zip`，双击 `Start ResearchMonitor.vbs`。
- 它会无窗口启动后台监控，并在浏览器里打开**设置页**：填收件邮箱、选择发信方式（Resend / QQ / 163 / Gmail / 其他 SMTP）、点「保存并发送测试邮件」、勾选开机自启。
- 自带 Python 3.12 与依赖，不会碰你的 conda 和 Python 环境。
- `Self-test.cmd` 做一次本机自检。自检会在最小化的命令行窗口里真实运行一个会报错的程序，验证三件事：能自动识别、能读到退出码、能读到终端窗口里的 traceback。
- Linux / macOS：`pip install researchmonitor-0.2.2-py3-none-any.whl`，然后运行 `rmon start`。

## 10. 数据与安全

- 数据库表 `runs` 新增 `profile`（时间线、指标、输出尾部、识别依据）和 `detect` 两列，新增 `rules` 表（监控 / 忽略规则），旧数据库启动时自动升级。
- agent 每分钟保存一次跟踪状态，所以 agent 重启或电脑重启后，仍能补发完整的报告。
- 面板只监听 127.0.0.1，需要登录 cookie，所有修改都用 POST + CSRF。
- 邮件中的命令行、报错和输出都经过密钥脱敏。
- 密码和 API Key 存在 Windows 凭据管理器。

## 11. 已知限制

- Linux 下读不到「不是本软件启动的进程」的退出码（操作系统限制），结论依赖输出、资源和文件证据。需要精确结果时可用 `rmon run`。
- 普通 Linux 终端（非 tmux）的屏幕输出无法从外部读取。
- Windows 下用 `pythonw` 或无控制台方式启动的程序，没有终端文字可读，只能依赖日志文件。
- WSL 里的任务在 Windows 侧只表现为 vmmem 进程。请在 WSL 里另外运行一份 rmon。
- 识别是启发式的：会有少量误判，可以用「监控它 / 忽略」一键纠正。
- 终端文字读取和退出码读取尚未在 Windows 真机验证，`Self-test.cmd` 会给出明确结果。

## 13. 独立代码审查（2026-10-16）

交付前请另一个审查者通读新代码，重点看 Windows。发现并已修复：
- 终端里有 tqdm 进度条时，增量读取会重复读旧内容，导致指标和完成信号被重复计入。现在以非进度行作为锚点，找不到锚点就不读，评估结果按内容去重。
- 从用户主目录启动脚本时，会把 AppData 里其它软件的日志当成任务输出。现在改为扫描脚本所在文件夹，并跳过 AppData、Library、系统和隐藏目录。
- 用过 CUDA 的空闲 Jupyter kernel 会被反复跟踪又丢弃，并留下大量空目录。现在必须真的在计算才算开始，丢弃后冷却 10 分钟，并删除目录。
- 实验关键词误匹配了解释器路径（`AppData` 中的 data），每个 Python 都白得 1 分。现在只看参数，按词边界匹配，并删掉 data、model 等过于宽泛的词。
- 终端读到空内容时被当成「可读」。
- 中文全角字符会导致终端文字按固定宽度切行出错。现在逐行读取，并合并自动换行。
- 面板线程与调度线程存在竞争。
- 恢复时一行出错会导致后面所有任务都不再跟踪。
- 设置页：端口填错时页面崩溃；中间结果间隔被意外重置。
- 旧版驱动下 NVML 进程列表为空。
- venv 安装时，读取终端文字的辅助进程会闪出窗口。
- 补充：Windows WDDM 模式下驱动不报告 GPU 进程时，改为通过进程是否加载了 CUDA 库来判断。
